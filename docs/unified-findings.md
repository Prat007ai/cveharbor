# Shared customer findings and remediation

The Customer Security Dashboard retains CVE, Published, Severity, Software / Asset, Vulnerability summary, Vulnerability Fix Status, and DevOps Ticket #. Its customer/environment filters and report exports retain their existing scope. Assign / View remediation creates or opens a shared record for that account-owned asset and CVE. Merely loading findings does not create records or send requests.

The shared record contains the same fix status, owner, target date, tickets, comments, status history, assignments and acknowledgements. Assign by email opens the existing reviewed and confirmed assignment flow on the tracker with the selected asset context. The tracker shows asset-linked work alongside explicitly labeled standalone records. Existing CVE-only records are not guessed or merged into asset findings. Recent activity provides entry points to updated records.

Internally, legacy keys remain unchanged. New work keys are a CVE plus an uppercase asset identifier separated by `~`; migration 0028 associates these keys with an owned inventory asset. Public CVE references always use the CVE portion. Assignment tokens, history, reviewer access, and reminder cycles keep using the existing record foreign keys, giving each asset independent progress. Private asset context appears in the requested assignment email and only after email verification on the reviewer page; the public acknowledgement page remains limited to public advisory information.

Linked writes go through the remediation workflow with an optimistic version and a reason for status changes. A database trigger projects the canonical status into the existing finding-status table for reports and dashboard readers in the same transaction. Unlinked findings retain their existing status behavior. The mapping is Needs Review/Open, Fix in Progress/Investigating, and Fixed/Patched/Remediated; Not Applicable and Accepted Risk are unchanged. Tickets remain append-only and retain their existing finding scope. Reviewer updates and owner comments reset only the linked record's inactivity period. Comments remain private to authenticated record owners and the relevant verified reviewer’s own activity; notification emails do not contain comments.

Migration 0028 is additive and repeatable, with no bulk backfill. Deleting an inventory asset also deletes its linked remediation and revokes access through existing foreign-key cascades, consistent with deleting the asset's findings. Linked records cannot be removed through the standalone tracker delete action; resolve them using their status. Existing 250-work-record capacity remains enforced. Reopening a shared record reloads current status and history; stale writes are rejected.

Deployment records a D1 Time Travel recovery bookmark, applies only migration 0028, runs SELECT-only schema/tenant probes, deploys the compatible Worker, and verifies protected routes. No production emails or customer records are used for release tests. The frontend uses versioned assets and exact-content production checks.

Validation includes the real Worker/SQLite integration test and browser flow through both views, cross-account/customer/asset isolation, retained tickets, both directions of status updates, reviewer updates, stale edits, reminder reset, migration reruns, asset deletion, responsive dialog sizes, and clearing private content on sign-out.
