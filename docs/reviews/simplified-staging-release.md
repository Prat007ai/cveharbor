## Routine development and release

- PR CI validates code, the historical manifest, security boundaries and synthetic application tests. Reviewed changes merge to main.
- The existing staging workflow serializes writes. It derives its source from GitHub's immutable SHA, validates the baseline and applied migration receipts, checks D1 Time Travel, applies only pending forward migrations, and updates the existing backend before the frontend. It verifies schema, runtime, private feed availability and Access boundaries. Production resources are never in its configuration.
- New routine schema changes go in `release/migrations/NNNN_description.sql`. D1's native migration ledger tracks application; a small checksum table detects edited/reordered applied migrations. Existing historical SQL/checksums are immutable. Local schema construction includes future forward SQL while the checkpoint-740 initialization plan stays frozen. Routine SQL is conservatively restricted to additive changes; data transforms, drops and resets require a separate reviewed maintenance operation.
- For pending staging migrations, the installed recovery control blocks new writes and waits briefly for active operations. If they do not drain within the bounded wait, it defers the migration and retains admission hold; it never discards active leases. A failure after migration starts retains maintenance for investigation. It never releases a pre-existing operator hold, expires leases, resets the DB or automatically restores.
- Successful staging emits a small receipt containing SHA, backend identity and completion status, without raw recovery bookmarks or exports. Production workflows verify its GitHub run/job/artifact provenance and exact SHA before requesting production environment approval. Failed/skipped/initialization-only/different-SHA runs cannot authorize publication. The two legacy Worker publishers are gated too.
- After production approval, the existing Worker workflow respects recovery controls, applies reviewed pending native additive migrations, deploys/verifies backend, then the existing frontend workflow requires matching backend/schema before publication. Production mutation jobs still share one concurrency lock. Frontend waiting happens before acquiring that lock, so it cannot prevent the required backend deployment from running. The publication job rechecks backend compatibility after acquiring its lock. The first Phase 1 rollout retains its documented integrity audit and explicit migration mode.
- Hourly intelligence collection/publication is unchanged and independent of these gates. Existing feed source/cutover flags, eight-hour freshness validation, digest and lifecycle email behavior are unchanged. Do not turn off the current feed source until its R2 replacement is separately validated and approved.

## Recovery and what is removed from routine staging

No routine staging export upload, recovery R2 bucket, `CF_STAGING_RECOVERY_EVIDENCE`, `CF_STAGING_APPROVED_COMMIT`, schema resume variable, repeat administrator token update, or manual backup deadline is required by the new lane. Those legacy inputs remain only in the historical pre-merge/exception workflow. Restricting the staging environment to main prevents that old branch from using its credentials after activation. No credentials are deleted automatically.

D1 Time Travel and the existing write hold remain available. A failed migration does not trigger a destructive automatic rollback: inspect D1 native migration status and receipts, prefer a reviewed forward repair, or explicitly approve a Time Travel restore within the supported retention period. Restore the database and compatible code as one reviewed recovery operation. Never blindly replay a migration with uncertain completion or overwrite a checksum gap. After a reviewed forward repair/drain, read the current `operations_control.revision` in the staging D1 console and dispatch this same main workflow with `simple_operation=resume`, `hold_revision` and a descriptive `recovery_reason`. Resume checks the complete schema, empty active-lease set, integrity and exact revision before releasing the hold; it does not deploy. This exceptional recovery action is intentionally explicit. Do not use the production-default recovery CLI against staging. Raw bookmarks/exports must stay private.

Production backup/recovery, approval and destructive-operation controls are not removed. A failed staging gate pauses publication, not the running production Workers or intelligence publisher. No database/resource creation is part of this change.
